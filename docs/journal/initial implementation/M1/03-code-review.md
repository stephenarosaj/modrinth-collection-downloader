**#1** -- `computeVisibleDependencyIds` (`src/core/projections.ts:68-100`) only traverses `required` dependencies starting from collection entries that are currently selected (`rootState.selection.on`). Meanwhile, `toFileTree` (`src/core/projections.ts:199`) and `toMrpack` (`src/core/projections.ts:288`) include any entry (collection or dependency) where `state.selection.on === true`. If a dependency entry has `selection: { on: true, source: 'user' }` (e.g., toggled on by the user) and its parent collection entry is later overridden via `set-version` or `changeEntryVersion` to a version that no longer requires that dependency, `recomputeSelectionAndRequiredBy` / `recomputeDependencyClosure` intentionally preserves `selection: { on: true, source: 'user' }` (per `docs/concepts.md` §7.2 user-choice preservation). However, `computeVisibleDependencyIds` no longer reaches that dependency from any root, so `toTables` hides the row from the UI while `toFileTree` and `toMrpack` still export its JARs into the download and `.mrpack` bundle, with no way for the user to see or deselect it in the table.
-> In `computeVisibleDependencyIds` (`src/core/projections.ts:68-100`), in addition to walking required dependencies of selected collection roots, also include any dependency entry that itself has `state.selection.on === true` in any environment (and walk its required dependencies transitively) so any entry that will be exported in `toFileTree` / `toMrpack` is guaranteed to be visible in `toTables`.

**#2** -- There are two divergent implementations of synchronous version-override recomputation: `reduceInstance` case `'set-version'` (`src/core/reducers.ts:375-434` + `recomputeSelectionAndRequiredBy` at `src/core/reducers.ts:251-365`) and `recomputeDependencyClosure` (`src/core/resolver.ts:1022-1208`, also called by `changeEntryVersion`). Specifically:
1. `reduceInstance` `'set-version'` (`src/core/reducers.ts:420`) only updates the target entry's `resolvedVersion` and calls `recomputeSelectionAndRequiredBy`, which never re-evaluates child dependency versions when the new parent version adds, changes, or removes a version pin (`dependency.versionId`).
2. `reduceInstance` `'set-version'` does not check `entry.support[action.env] === 'unsupported'` before setting `resolvedVersion`, unlike `recomputeDependencyClosure` (`src/core/resolver.ts:1042`).
3. `recomputeSelectionAndRequiredBy` calls `recomputeRequiredByInEnvironment` (`src/core/reducers.ts:86-111`), which adds `requiredBy` edges from every entry with `resolvedVersion !== null` (even unselected/orphaned dependency entries), whereas `recomputeDependencyClosure` (`src/core/resolver.ts:1065-1102`) only adds `requiredBy` edges along the reachable BFS closure from selected collection roots.
4. In `recomputeSelectionAndRequiredBy` (`src/core/reducers.ts:276-361`), Pass 1 emits an `auto-selected` change whenever an unselected dependency is newly listed by the newly set version, even if its parent collection entry has `selection.on === false`; Pass 2 then sees the dependency is unreachable from selected roots and immediately reverts it to `{ on: false, source: 'none' }` while emitting a second `auto-deselected` change in the same `Change[]` array.
-> Unify synchronous version-override recomputation by having `case 'set-version'` in `reduceInstance` delegate to `recomputeDependencyClosure` (or extract a single shared fixed-point closure helper used by `resolveCollection`, `recomputeDependencyClosure`, and `reduceInstance` `'set-version'`) so version pinning, reachability, `requiredBy`, and `auto-selected` / `auto-deselected` changes behave identically across all APIs.

**#3** -- `hasSelectionChangedFromDefault` (`src/core/reducers.ts:558-561`) returns `true` whenever any entry has `state.resolution === 'user'` (`if (state.resolution === 'user') return true;`), in addition to checking whether `state.selection` differs from `computeInitialSelection(instance)`. However, `resetInstanceSelection` (`src/core/reducers.ts:505`) and `reduceInstance(instance, { type: 'reset-selection' })` (`src/core/reducers.ts:436-475`) only reset `state.selection` back to `computeInitialSelection(instance)` and never reset `state.resolution` or `state.resolvedVersion` (nor does `Instance` store the initial default resolved version when `candidates` is empty or pinned). Consequently, once a user overrides any entry's version (`resolution: 'user'`), `hasSelectionChangedFromDefault(instance)` returns `true`, and clicking "Reset Selection" (`resetInstanceSelection` / `reset-selection`) produces an instance where `hasSelectionChangedFromDefault(resetResult.instance)` still returns `true`, leaving a "Reset Selection" UI button permanently enabled as a no-op.
-> Either scope `hasSelectionChangedFromDefault` strictly to selection state (`on` and `source` compared against `computeInitialSelection(instance)`) so it matches what `resetInstanceSelection` actually resets, or if `reset-selection` is also meant to reset user version overrides, store/recompute the default resolved version and `resolution` in `resetInstanceSelection` / `recomputeDependencyClosure`.

**#4** -- In `src/core/resolver.ts`, initial resolution (`computeEnvironmentClosureInMemory`, lines 404-552) uses a fixed-point loop (`MAX_CLOSURE_ITERATIONS = 32`) because a deeper node in the dependency graph can pin a dependency (`projectId` + `versionId`) after that dependency was already visited via a nearer unpinned edge, changing its `resolvedVersion` and thus its transitive dependencies. By contrast, `recomputeDependencyClosure` (lines 1065-1156) uses a single-pass BFS with a `visited` set (`if (visited.has(currentId)) continue; visited.add(currentId);` at line 1069) BEFORE computing pinned/highest versions (lines 1105-1156). This causes three concrete bugs after `changeEntryVersion` or `recomputeDependencyClosure`:
1. If root A depends on X (unpinned) and root B depends on Y -> X (pinned to `v1`), the BFS visits X first at depth 1 using X's previous version (`v2`), expands `v2`'s dependencies, and marks X `visited`. When lines 1105-1156 later resolve X to pinned `v1`, `v1`'s dependencies are never traversed, leaving `v1`'s required dependencies unselected (`on: false`) and without `requiredBy` edges.
2. At lines 1110-1129, `recomputeDependencyClosure` collects pins from `for (const [otherId, otherEntry] of Object.entries(nextEntries))` across ALL entries in `nextEntries` (including unselected collection entries and unreachable orphaned dependencies) rather than only entries in the active closure (`visited`).
3. When a parent changes version so that it no longer pins dependency X (`pinnedIds.length === 0`), lines 1131-1155 only recompute `resolvedVersion` if `state.resolvedVersion === null`, leaving X permanently stuck on the old pinned version with `resolution: 'pinned'` instead of falling back to Rule 2 (`candidates[0]`, `resolution: 'newest'`).
-> Replace the single-pass BFS + separate pin pass in `recomputeDependencyClosure` with the same iterative fixed-point algorithm used by `computeEnvironmentClosureInMemory` (parameterized to preserve `resolution === 'user'` overrides), and when an entry had `resolution === 'pinned'` (or `newest`) in the previous state, re-evaluate its version from active closure pins or fall back to `candidates[0]` (`resolution: 'newest'`).

**#5** -- `changeEntryVersion` (`src/core/resolver.ts:1328-1402`) has two defects when discovering transitive dependencies for a newly selected version:
1. At lines 1335-1342, `knownProjectIds` is seeded with all existing `Object.keys(instance.entries)`, and any dependency in `newVersion.dependencies` whose `projectId` is already in `knownProjectIds` is skipped (`if (!knownProjectIds.has(dep.projectId))`). If the user switches an entry to a version that pins an already-known dependency `D` to a different version `D_v2` (or newly brings an already-known dependency `D` into the active closure), and `D_v2` requires a brand-new transitive dependency `T` not yet in `instance.entries`, `changeEntryVersion` never inspects `D_v2.dependencies` and never fetches `T`.
2. Conversely, for a newly discovered dependency `N`, lines 1396-1402 iterate over *every* historical version returned by Modrinth for `N` (`for (const v of versions) { for (const dep of v.dependencies) ... }`) instead of resolving which version of `N` is actually selected in `env`, fetching unrelated projects required only by ancient or incompatible versions of `N`.
-> In `changeEntryVersion`, run the fixed-point closure resolution loop per environment (`computeEnvironmentClosureInMemory` with the updated version override); whenever a resolved version in the closure references a required `projectId` or pinned `versionId` not yet cached, fetch that project and its compatible/pinned versions and repeat until the closure converges.

**#6** -- `hasPinConflictInEnvironment` (`src/core/status.ts:225-248`) has three flaws that cause false-positive and false-negative `PIN_CONFLICT` errors:
1. At line 239 (`if (state.candidates.length <= 1) return true;`), when a dependency has 0 or 1 compatible version in `state.candidates` (common when a mod has a single release for a Minecraft version) and two parents pin `v1` (compatible) and `v2` (incompatible), `pinnedIds.size` is 2 and `state.candidates.length <= 1` immediately returns `true` (`PIN_CONFLICT`) without filtering out the incompatible pin `v2`. Whether `PIN_CONFLICT` fires thus depends on whether an unrelated second compatible candidate `v3` exists.
2. `hasPinConflictInEnvironment` is called even when the dependency's own version was manually overridden by the user (`state.resolution === 'user'`), continuing to report `PIN_CONFLICT` (`error`) after the user manually resolved the conflict.
3. `hasPinConflictInEnvironment` iterates over all `Object.values(instance.entries)` checking `otherState.selection.on` (which can include unselected-root remnants or entries outside the active environment closure) rather than checking active parents in `state.requiredBy`.
-> In `hasPinConflictInEnvironment`: (1) return `false` if `state.resolution === 'user'`; (2) only inspect parent entries that are in `state.requiredBy` (or active in the environment's closure); and (3) filter `pinnedIds` against compatible `candidateIds` whenever `state.candidates.length > 0` (`const compatiblePins = [...pinnedIds].filter((id) => candidateIds.has(id)); return compatiblePins.length > 1 || (compatiblePins.length === 0 && pinnedIds.size > 1);`).
